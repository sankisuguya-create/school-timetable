# 利用開始前の運用設計（最大40人）

この文書は、教職員が実際に使い始める日に起こりうる問題と、その予防・検知・復旧方法を
まとめた運用設計である。機能仕様の正本は [`spec.md`](spec.md)、設置手順は
[`setup.md`](setup.md) とする。

## 1. 結論

最大40人という**在籍ユーザー数そのもの**は、この構成を変更する理由にはならない。
画面は各端末で動き、読み込みは開いた年度・週に絞り、保存は差分をまとめて送るためである。

ただし、次の3点は利用開始時に実際に起こりうる。

1. 初回アクセス時のアカウント・共有・デプロイ設定の誤り
2. 木曜夕方などに保存が集中したときの `LockService` 待ち（最悪40人が直列に並ぶ）
3. 同じコマを複数人が編集したときの競合

2と3は「利用人数が40人だからデータが壊れる」問題ではない。現在の実装は書き込みを直列化し、
古い状態からの保存をコマ単位で止め、未保存データを端末に残す。したがって主な残余リスクは
**待ち時間と、再操作が必要なこと**である。利用開始前に下記の受入試験を行い、開始後1週間は
数値と問い合わせを記録する。

## 2. 前提を分ける

容量判断では、次の数を混同しない。

| 数 | この学校での上限 | 意味 |
|---|---:|---|
| 登録・利用者 | 40人 | URLを渡す教職員の総数 |
| 同時閲覧 | 40人 | 同じ時刻に画面を開く最悪ケース |
| 同時保存 | 40人 | 全員がほぼ同時に「保存」を押す、意図的な負荷試験ケース |
| 同一コマ編集 | 通常2〜数人 | データ競合が起きる単位。人数全体より重要 |

通常運用では同時保存40件は考えにくいが、職員会議で一斉に案内した直後は起こりうる。
「40アカウントがある」だけの確認では、このピークを検証したことにはならない。

## 3. リスクと対応

| 優先 | 起こりうること | 既存の予防策 | 利用開始前／開始後の対応 | 復旧・判定 |
|---|---|---|---|---|
| 高 | 教員が入れない、または児童が入れる | メールドメイン完全一致、全APIの `Gate.check()`、閉じる側に倒す判定 | 教職員2人、別アカウント1人、児童1人で実URLを確認。シートは管理者だけに共有 | 児童に週案が見えたら即時利用停止。デプロイ、関門、シート共有を直して全検査を再実行 |
| 高 | 一斉保存が30秒のロック待ち上限に達する | 差分一括保存、打鍵ごとの送信をしない、失敗分を端末に保持 | 40端末で段階負荷試験。20人、30人、40人の順に同時保存し、管理画面の待ち時間を採取 | 「保存ずみ」になるまで閉じない。失敗表示なら少し待って再度保存。未保存件数が0なら復旧完了 |
| 高 | 同じコマの更新が衝突する | `expectedAt` による楽観的競合制御。競合したコマは書かず、双方に通知 | 2端末で同一コマを同時編集する受入試験を行う | 競合窓で最新を読み、必要なら内容を入れ直す。無言で片方が消えたら利用停止条件 |
| 高 | 通信断やタブを閉じたことで入力が未送信になる | 未送信・送信中の内容を端末の `localStorage` に保持し、次回起動時に再送 | Wi-Fiを切った状態で編集・保存・再接続を試す。「未保存」表示の読み方を初回説明に入れる | 同じブラウザ・同じ端末で開き直す。未保存0とシート反映を確認するまで端末データを消さない |
| 中 | 全員が一斉に初回表示し、起動が遅い | 起動情報を1往復にまとめ、必要な週だけ先に読む | 一斉ログイン試験で入口表示と週表示を別々に計測 | 読み込み失敗が続く場合は時間をずらす。まずGoogle Workspace障害とアカウントを切り分ける |
| 中 | 古いタブ／古いデプロイを使い続ける | 版・版の日付・接続ファイル名を管理画面に表示 | 案内文に正しいURLと期待する版を明記。公開後は既存デプロイを「新バージョン」で更新 | 問い合わせ時は管理画面の1行、時刻、クラス、週、操作を必ず受け取る |
| 中 | 基本時間割・クラス・時程などの初期データ誤り | 年度検査と行番号付き警告 | 管理者と担任各1人が、全学年・専科・A/B週を目視確認 | 設定表を修正し、年度検査を再実行。週案データの一括削除で直そうとしない |
| 中 | GAS／Sheetsのサービス上限や一時障害 | 往復削減、まとめ書き、ローカル未送信保持 | 利用するGoogle Workspace契約の最新のApps Script上限を管理者が公式資料で確認 | 全員同時の失敗は個人操作よりサービス状態を疑う。入力は端末に残し、復旧後に再送 |
| 中 | 年度内にシートが既定1000行を超える | 書く前に行・列を伸ばす。年度末退避で1年分に抑える | 年度途中に年度検査、年度末に退避手順を実施 | 保存時間が2秒を継続して超えたら、仕様13節の分割判断へ進む |
| 低 | ブラウザ差、印刷倍率、端末制限 | 印刷設定を画面から変更可能 | 学校で実際に使うChrome環境とプリンタでB5/B4を1枚ずつ確認 | 対応ブラウザへ統一。印刷は実寸確認が終わるまで全員展開しない |

## 4. 利用開始前の受入試験

テスト用の週・コマを決め、本番データと混ぜない。40人を一度に集められない場合は、
複数タブで人数を水増しして「正しく使えた」とは判定しない。GASの実行主体・ブラウザ保存領域・
アカウントが同じになり、本番と条件が異なるからである。

### A. 必須（開始可否を決める）

1. リポジトリ記載の6検査をすべて通す。
2. 実URLを教職員2人で開き、児童1人では拒否されることを確認する。
3. 2人が同じコマを異なる内容で編集し、片方が競合として止まり、最新内容を再取得できることを確認する。
4. 1人が通信を切って編集し、再接続・再保存後に未保存件数が0になることを確認する。
5. 20人→30人→40人の順に、各人が**別のコマ**を編集して同時保存する。
6. 次に2〜3人だけが同じコマを編集し、負荷とデータ競合を分けて確認する。
7. 各段階で、成功数、失敗数、画面の最大ロック待ち、最大書き込み時間、最大往復時間を記録する。

**開始可**の条件は、権限漏れ0件、無言のデータ消失0件、全端末の未保存最終0件である。
待ち時間だけが長い場合はデータ安全性の不合格とは分け、次の基準で運用または改修を選ぶ。

### B. 性能の判定基準

| 観測 | 判断 |
|---|---|
| 書き込み時間が最大2秒以下、ロック待ちが一時的 | 現構成で開始。開始後1週間監視 |
| 書き込み時間が2秒超を繰り返す | シート肥大・全面書き戻しを調査し、仕様13-2の年度分割を検討 |
| ロック待ちだけが長い | 保存時刻を分散。40人一斉操作を避ける。部分更新は実測後にだけ設計する |
| 30秒待ち切れず失敗する | 未保存保持と再保存で復旧できることを確認し、開始時は学年ごとに数分ずらす |
| 無言の消失、別コマの破損、未保存0なのに未反映 | **開始不可**。性能改善ではなくデータ整合性障害として修正する |

## 5. 初日の展開方法

1. 最初は管理者3人と各学年代表だけで30分使う。
2. 問題がなければ、学年ごとに数分ずらして残りへURLを案内する。
3. 案内には「保存ずみを確認して閉じる」「赤い帯があれば再保存」「競合時は最新を見る」だけを書く。
4. 問い合わせ窓口を1人に決め、管理画面の版情報、発生時刻、開いた週・面、操作、表示文を収集する。
5. 初週の木曜夕方に、管理画面の直近20回の最大値を各学年代表から回収する。

問い合わせ件数を性能値と混ぜない。「使い方が分からない」と「保存処理が遅い」と
「保存内容が壊れた」は別々に数える。

## 6. 監視と改修の優先順位

常時監視サーバや大きな監査ログは、この規模では追加しない。運用負担のほうが大きい。
画面が既に持つ直近20回の最大値と、初週の簡単な記録で判断する。

1. **データ安全性**：無言の消失、誤った相手への上書き、権限漏れは1件で利用停止。
2. **復旧可能性**：失敗しても未保存件数が残り、再保存できること。
3. **待ち時間**：書き込み時間とロック待ちを分けて測る。
4. **最適化**：実測で基準を超えた箇所だけを直す。

40人向けという理由だけでキャッシュや並列書き込みを先に導入しない。キャッシュは古い週案を
返す可能性を増やし、ロックを細分化すると複数シートにまたがる操作の原子性を失う。
まず保存時刻の分散で運用し、それでもロック待ちが問題になる場合に限り、コマ単位の部分更新を
「競合検知を維持すること」「失敗時に全体を中途半端にしないこと」を受入条件として設計する。

## 7. 外部上限の確認先

Apps Scriptの割当・制限は契約やGoogle側の変更に依存するため、数値をこのリポジトリへ固定しない。
利用開始日と年度初めに、管理者が以下の公式資料を確認して日付と確認者を運用記録へ残す。

- [Apps Script services quotas](https://developers.google.com/apps-script/guides/services/quotas)
- [Apps Script best practices](https://developers.google.com/apps-script/guides/support/best-practices)
- [Google Workspace Status Dashboard](https://www.google.com/appsstatus/dashboard/)
